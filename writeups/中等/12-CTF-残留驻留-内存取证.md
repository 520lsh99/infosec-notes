# CTF 练习：残留驻留（内存取证 · 页表翻译 · 异或还原）

> 平台：CTF² / Daily Hack（Forensics · Medium · 300 分）
> 环境：浏览器取证工作台（read-only），镜像 ram.raw（64 MiB / 16384 页 × 4096）
> 日期：2026-11-19
> 性质：平台提供的授权靶场

---

## 一、目标

离线镜像 `ram.raw` 里有一个已经「从任务链表消失」的采集进程，它把秘密留在了物理内存里。要通过两份进程枚举对账找出它，再沿页表把秘密取回。

## 二、工作台信息

```
案件：2261-04   主机：billing-vm2
镜像：ram.raw  67108864 字节  页大小 4096  共 16384 页
关注进程：4471 (colsvc)
```

采集记录关键点：
- 13:58Z 崩溃处理器写了 `core.4471`（gcore 风格）
- 14:02Z 采集 `/proc` 快照（此时 4471 仍驻留）
- 14:04Z 两次枚举（任务链表 vs 池签名扫描）**结果不一致**，要求对账

## 三、复现过程

### 3.1 进程枚举对账

枚举 A（内核任务链表）：

```
PID  PPID COMM
1    0    systemd
2    0    kthreadd
...
4102 1    collector-sup
4402 4102 colsvc-watch
4412 4102 collector-agent
```

枚举 B（池签名扫描）：

```
... 同上 ...
4412 4102 collector-agent
4471 4412 colsvc        ← 只在 B 里出现
```

**差异：PID 4471 `colsvc`**——它已从任务链表摘下，但内存里的 `task_struct` 还在。

### 3.2 找核心转储的缺口

`/proc/4471/maps`：

```
55f0c19f8000-55f0c1a0b000 r-xp  /usr/local/bin/colsvc
55f0c1c0b000-55f0c1c0d000 rw-p  /usr/local/bin/colsvc
55f0c2d8e000-55f0c2d9f000 rw-p  [heap]
7f5c39e1a000-7f5c39fb0d000 r-xp  libc.so.6
7f5c39fd0000-7f5c3a03f000 r--p  libc.so.6
7f5c3a03f000-7f5c3a063000 r-xp  libm.so.6
7f5c3a03f000-7f5c3a0f8000 rwxp  [anon:telemetry]   ← 可疑
7ffd2c4a3000-7ffd2c4c4000 rw-p  [stack]
```

`core.4471` 的 LOAD 段只覆盖：
- colsvc text/data
- libc / libm
- main thread stack

**缺失：`[heap]` 和 `[anon:telemetry]`**——秘密只能在物理镜像里找。

### 3.3 拿密钥

`/proc/4471/environ`：

```
INV=4471
COL_KEY=quasar
PATH=/usr/local/bin:/usr/bin:/bin
HOME=/var/lib/colsvc
LANG=C.UTF-8
```

→ XOR 密钥 = `quasar`

### 3.4 页表翻译

`/proc/4471/pagemap` 给了 `[anon:telemetry]` 三个页：

```
0x7f5c3a0f5000  0x8000000000003a21
0x7f5c3a0f6000  0x8000000000003a22
0x7f5c3a0f7000  0x8000000000003a23
```

- 最高位 `0x8000...` 是 present 位
- 低 55 位是 PFN：`0x3a21`

物理地址：

```
PFN × 页大小 = 0x3a21 × 0x1000 = 0x3a21000
```

### 3.5 读物理内存

用「镜像浏览器」按物理偏移读：

```
0x3a21000，长度 64
```

得到：

```
54 4c 4d 31 2a 00 00 00 32 21 27 41 ...   |TLM1*...2!'A...|
```

前 8 字节 `TLM1*` + 3 个 0 是**文件头**，跳过。

从 `0x3a21008` 开始再读 64 字节：

```
32 21 27 41 1a 47 48 41 03 41 55 13 45 58 03 4b
03 41 5c 41 07 4a 07 5f 10 46 59 4b 4c 45 43 47
03 4a 07 17 44 46 02 41 00 0f 00 00 00 00 00 00
```

### 3.6 异或还原

密钥 `quasar`（循环使用），逐字节异或：

```
0x32 ^ 'q' = 'C'
0x21 ^ 'u' = 'T'
0x27 ^ 'a' = 'F'
0x41 ^ 's' = '2'
0x1a ^ 'a' = '{'
...
```

得到：

```
CTF2{594b24a4-b8b3-4f9f-a388-722b9fe53c2a}
```

（末尾 `quasarquasar` 是零填充解密出的垃圾）

## 三·五、复盘四问

### 推理链（为什么这么做）

**第 1 步：为什么先对账两份进程枚举**

- 我在想：题面说「一份枚举里没有它」，那差异点就是隐藏进程。
- 验证：A（任务链表）没有 4471，B（池扫描）有 4471 `colsvc`。
- 所以：目标进程 = 4471，且它已 unlink 但内存对象还在。

**第 2 步：为什么要比 maps 和 core**

- 我在想：秘密不会在普通代码段，应该在「core 没覆盖」的段里。
- 验证：maps 有 `[heap]` 和 `[anon:telemetry]`，core 的 LOAD 段没有它们。
- 所以：去物理镜像里找这两段。

**第 3 步：为什么去 environ 找密钥**

- 我在想：程序要解密自己的数据，密钥很可能在环境变量（部署常见做法）。
- 验证：`COL_KEY=quasar`。
- 所以：XOR 密钥 = `quasar`。

**第 4 步：为什么用 pagemap 而不是瞎搜物理内存**

- 我在想：`ram.raw` 有 16384 页，盲搜慢且容易撞到巧合数据。
- 验证：pagemap 给出虚拟页 → PFN，`0x3a21`。
- 所以：物理地址 = `0x3a21 × 0x1000 = 0x3a21000`，一次命中。

**第 5 步：为什么读到 `TLM1*` 后要加 8 字节偏移**

- 我在想：前 8 字节是 `TLM1*` + 3 个 0，像文件头，不像密文。
- 验证：从 `0x3a21008` 重新读，首字节 `0x32` 与 `'q'` 异或正好是 `'C'`。
- 所以：密文起点 = 物理基址 + 8。

**第 6 步：为什么末尾会出现 `quasarquasar`**

- 我在想：解密出的是「零填充」，零异或密钥就会还原出密钥本身。
- 所以：flag 到 `}` 就结束，后面是填充垃圾。

### 载荷/命令是怎么来的

- **来源**：全手工；读镜像用页面上的「镜像浏览器」输入偏移与长度。
- **为什么偏移写 `0x3a21008`**：物理基址 + 8 字节文件头。
- **为什么长度 64**：flag 约 43 字节，64 足够覆盖。

### 逐段解释

| 动作 | 作用 |
|---|---|
| 两份枚举对账 | 找出 unlink 的隐藏进程 4471 |
| `/proc/4471/maps` | 定位可疑段 `[anon:telemetry]`、`[heap]` |
| `core.4471` LOAD 段 | 确认哪些段**没**被转储（缺口） |
| `/proc/4471/environ` | 取 XOR 密钥 `quasar` |
| `/proc/4471/pagemap` | 虚拟页 → 物理帧号（PFN） |
| `PFN × 4096` | 物理地址 |
| 读 `0x3a21008` | 跳过 TLM1 文件头，取密文 |
| 逐字节 XOR | 还原明文 |

### 失败尝试与坑

| 尝试 | 结果 | 原因 |
|---|---|---|
| 直接从 `0x3a21000` 异或 | 开头是 `%9,BK` 乱码 | 没跳过 8 字节文件头 |
| 把 pagemap 整个值当 PFN | 地址错 | 最高位 `0x8000...` 是 present 标志 |
| 读未采集的页 | 全 0 | 镜像未采集的页回读为 0，不是数据 |
| 先看 heap | 没找到 | 秘密在 `[anon:telemetry]` |

### 自测

**Q1**：隐藏进程为什么用「两份枚举」而不是直接看 ps？
**A**：它已从任务链表 unlink，链表遍历看不到，但内存里的对象还在，池扫描能找到。

**Q2**：物理地址怎么算？
**A**：`PFN × 页大小`，本题 `0x3a21 × 0x1000 = 0x3a21000`。

**Q3**：为什么解密结果末尾有 `quasarquasar`？
**A**：密文尾部是零填充，零异或密钥就还原出密钥本身。

## 四、原理

| 环节 | 手法 |
|---|---|
| 隐藏进程 | 从任务链表 unlink，但内存对象仍在 → 池扫描可发现 |
| 核心转储缺口 | gcore 只 dump 部分段，anonymous 段可能缺失 |
| 页表翻译 | `/proc/pid/pagemap` 给出虚拟页 → 物理帧号 |
| 特殊内存 | `rwxp` 的 `[anon:telemetry]` 是自映射的可执行匿名页，常见于恶意驻留 |

## 五、修复与检测

1. **监控 anon 可执行内存**（`rwx` 匿名映射）——正常程序很少见。
2. **定期做内存取证对账**：任务链表 vs 池扫描，发现 unlink 的隐藏进程。
3. **完整采集**：核心转储应覆盖所有 private 段，或用全内存镜像。
4. **敏感数据不落裸内存**：密钥应加密存放、用完即清。

## 六、踩坑

1. **文件头要跳过**：`TLM1*` + 8 字节头，直接异或会错位。
2. **偏移要加 8**：`0x3a21008` 而不是 `0x3a21000`。
3. **pagemap 的最高位是标志位**，不能当 PFN 用。
4. **零页不是证据**：镜像未采集的页读回全零，别把它当数据。

## 七、收获

- 走通了一次完整的内存取证链：进程对账 → maps → core 差异 → pagemap → 物理读 → 解密。
- 理解了「虚拟地址 → 页表 → 物理地址」的换算。
- 认识到「进程从链表消失 ≠ 进程不存在」。
