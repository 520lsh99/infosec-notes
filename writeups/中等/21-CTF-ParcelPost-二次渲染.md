## 0. 一句话总结

「嵌套个性化展开」会把**用户字段当模板二次渲染**，而且第二次渲染的作用域升级为 `system`；于是字段里写 `{{ settings.preview_secret }}` 就能读到内部保留值。

## 1. 题目给了什么

- 消息运营面板：正文模板 + 收件人/订单/优惠码三个字段
- 按钮：「嵌套个性化展开 / 仅标准渲染」+「以收件人身份预览」
- 渲染诊断：变量映射 + 阶段追踪
- 宏注册表：

```
settings.brand_name        system   可用
settings.support_email     system   可用
settings.legal_footer      system   可用
settings.preview_secret    system   内部保留
```

- 提示：「字段以数据方式注入，输出自动转义」「找出系统作用域中仅被内部保留的渲染密钥」

## 2. 我观察到什么

| 观察 | 位置 | 说明 |
|---|---|---|
| 占位符是 `{{ 标识符 }}` | 页面提示 | 模板语法 |
| 诊断：`收件人姓名 → recipient_name → pass 1 · user` | 渲染诊断 | 第一次渲染在 user 作用域 |
| 诊断：`PASS 1 scope=user autoscape=on escaped=true` | 阶段追踪 | 只有 pass1，说明还有后续可能的 pass2 |
| 正文写 `hello` 时字段内容不出现 | 预览 | **字段只有被正文引用才会进渲染链** |
| 正文写 `{{ recipient_name }}` + 字段 `world` → 预览 `world` | 实验 | 链路正常 |

## 3. 推理链（为什么这么做）

### 第 1 步：为什么盯上「嵌套个性化展开」

- **我在想**：「嵌套」+「个性化展开」几乎等于「字段值会被二次渲染」。
- **为什么危险**：二次渲染时，上一次的「数据」会变成「模板代码」。
- **验证计划**：先确认一次渲染正常，再用它测二次渲染。

### 第 2 步：为什么正文必须先写 `{{ recipient_name }}`

- **我在想**：字段是「数据注入」，如果正文不引用，渲染器就没理由展开它。
- **验证**：正文 `hello` 时预览只有 `hello`；改成 `{{ recipient_name }}` 后 `world` 出现。
- **所以**：字段要进渲染链，正文必须引用。

### 第 3 步：为什么不直接猜 `preview_secret`，而是先测 `{{ settings }}`

- **我在想**：不知道作用域里有没有 `settings`，直接猜会浪费次数。
- **验证**：字段填 `{{ settings }}`。
- **结果**：预览显示 `<__main__.SystemSettings object at 0x7f6d823cb200>`。
- **所以**：`settings` 对象存在，而且是 **Python 对象**（`repr` 暴露了模块名）。

### 第 4 步：为什么下一个测 `brand_name`

- **我在想**：知道对象存在，还要确认「属性链」能用。
- **验证**：`{{ settings.brand_name }}` → `ParcelPost Merchant Ops`。
- **所以**：`{obj.attr}` 这种 Python 格式化语法被支持。

### 第 5 步：取内部保留值

- **验证**：`{{ settings.preview_secret }}`。
- **结果**：预览出现 flag。
- **所以**：漏洞成立 —— 二次渲染作用域是 system，且属性访问无限制。

## 4. 代码（载荷）是怎么来的

- **来源**：手写在浏览器输入框里，无脚本。
- **构造逻辑**：

```
第一层（正文）：{{ recipient_name }}   ← 让字段被引用
第二层（字段）：{{ settings.preview_secret }}  ← 二次渲染时执行
```

- **为什么用 `settings.xxx` 而不是别的写法**：诊断说明系统宏以 `settings.` 开头；`{{ settings }}` 的 `repr` 也证明对象名就是 `settings`。

## 5. 代码（载荷）逐段解释

| 片段 | 作用 |
|---|---|
| `{{` `}}` | 模板定界符，告诉渲染器「里面是表达式」 |
| `recipient_name` | 第一次渲染时被字段值替换 |
| 字段值 `{{ settings.preview_secret }}` | 第一次渲染只是原样输出（数据），第二次渲染才被求值 |
| `settings` | 系统作用域对象（`__main__.SystemSettings`） |
| `.preview_secret` | 属性访问，取出内部保留字段 |

## 6. 为什么这样就成功

| 条件 | 要求 | 满足方式 |
|---|---|---|
| 二次渲染存在 | 字段值被再次当模板 | 选「嵌套个性化展开」 |
| 作用域升级 | 第二次用 system 而非 user | 服务端实现缺陷 |
| 属性可读 | 允许 `obj.attr` | Python 格式化语法 |
| 字段进链 | 正文引用字段 | 正文写 `{{ recipient_name }}` |

## 7. 失败尝试与排除

| 尝试 | 结果 | 为什么失败 |
|---|---|---|
| 直接把 `{{ settings.preview_secret }}` 放正文 | 拿不到 | 正文只在 user 作用域渲染 |
| 字段填 payload 但正文是 `hello` | 预览只有 hello | 字段未被引用，不进渲染链 |
| 一开始不测 `{{ settings }}` 就猜 | — | 会浪费尝试，且无法确认对象是否存在 |
| 用 `${{7*7}}` 之类试探 | pass1 输出 true，语义不符 | 该引擎不是 JS 模板 |

## 8. 原理

- **二次渲染（double template rendering）**：把用户输入再次交给模板引擎，等于把数据当代码执行。
- **作用域混淆（scope confusion）**：第二次渲染用了更高权限的上下文，导致越权读。
- **Python 格式化**：`"{obj.attr}".format(obj=...)` 支持属性链，天然适合越权读字段。

## 9. 防御

1. 用户数据只渲染一次，渲染结果不再进模板引擎。
2. 必须嵌套时，第二次渲染限制为同一受限作用域。
3. 用沙箱模板引擎，禁止属性链访问。
4. 系统宏与用户上下文物理隔离。
5. 输出保持转义 + 校验。

## 10. 复盘自测

**Q1**：为什么字段单独填 payload 没用？
**A**：正文不引用该字段时，渲染器不会展开它。

**Q2**：`<__main__.SystemSettings object at 0x...>` 说明了什么？
**A**：模板引擎是 Python 的 `str.format` 系；作用域里有 `settings` 对象。

**Q3**：这题漏洞的本质是什么？
**A**：数据被二次当作模板执行，且执行作用域被升级到 system。
