## 0. 一句话总结

对 16 字节密钥逐字节做 CPA（相关性功耗分析），用「方差选点 + (密钥, 掩码) 暴力」恢复 15 个字节；唯一被掩码的那轮利用 calibration 模式的 **sticky 掩码复用** 补齐，最后用 SHA-256 计数器流解密保险库。

## 1. 题目给了什么

- 网页控制台，命令：

```
capture <32位hex明文> [mode]   采一条轨迹（0 普通 / 1 校准）
dump        读公开寄存器与公开随机数
vault       读封存密文
rom         列出 S 盒
export      下载最近一次轨迹
```

- 提示：器件只在功耗轨迹里泄漏查表结果；其中一轮被掩码；校准开关有掩码复用缺陷；耗时读数是干扰。

## 2. 我观察到什么

| 观察 | 位置 | 说明 |

## 3. 推理链（为什么这么做）

### 第 1 步：为什么要找 REST 接口，而不是手点页面

- **我在想**：CPA 需要几十上百条轨迹，页面一次一条，手点不现实。
- **怎么验证**：F12 → Network，点一次「采样」，看到 `GET /api/capture?pt=...&mode=...&nonce=...`。
- **结论**：可以脚本化批量采集。

### 第 2 步：为什么先假设「尖峰高度 ∝ 汉明重量」

- **我在想**：S 盒查表的功耗模型，最常见的是 `HW(S[p^k])`（汉明重量）或查表值本身。
- **怎么验证**：固定 nonce，扫第 0 字节明文 0..255，取第 0 个尖峰幅度，与两种模型算相关系数。
- **结果**：最高只有 0.2。
- **所以**：模型没错，但**采样点选错了**，或者被掩码。

### 第 3 步：为什么改成「方差选点 + (k, mask) 二维暴力」

- **我在想**：如果尖峰附近的某个采样点才携带信息，就应该挑「随明文变化最剧烈」的点 → 用方差排序。
- **为什么要暴力 mask**：normal 模式下掩码由 nonce 决定，固定 nonce 后 mask 恒定但**未知**，模型变成 `HW(S[p^k] ^ mask)`。
- **怎么验证**：对每个字节，在窗口 `8+32i` 内按方差取前 3 个点，对每个点暴力 256×256 组 `(k, mask)`，算相关系数。
- **结果**：15 个字节相关系数 0.97+，只有 byte 11 是 0.34。
- **所以**：byte 11 就是「被掩码保护的那一轮」。

### 第 4 步：为什么 mode=1 能救 byte 11

- **我在想**：`mask_policy` 说 calibration 是 **sticky**，即掩码复用、跨采集不变。
- **怎么验证**：用 `mode=1` 重新采 160 条，对 byte 11 做同样的 `(k,mask)` 暴力。
- **结果**：相关系数 0.98，`k=205`。
- **所以**：掩码复用把「未知掩码」变成「常量掩码」，暴力即可。

### 第 5 步：为什么解密要「试参数组合」

- **我在想**：只给了 `cipher=SHA-256 counter stream XOR`，没给拼法。
- **怎么验证**：枚举 `key‖nonce‖ctr` 的 6 种排列、ctr 的 4/8 字节、大小端、起始 0/1，用「可打印字符比例」打分。
- **结果**：`SHA256(key ‖ nonce ‖ ctr_be32)` 得分 1.0，明文即 flag。

## 4. 代码是怎么来的

- **来源**：全部自己写（Python）。
- **为什么用 `(k, mask)` 暴力**：不知道掩码，但掩码只有 256 种可能，和密钥一起枚举也就 65536 组。
- **为什么用方差选点**：不知道泄漏落在窗口内哪一点，方差最大的点最可能带信息。
- **为什么 160 条**：相关系数需要样本量；160 条已让正确密钥的相关系数稳定在 0.97+。

```python
IDX = np.arange(256)[:,None] ^ np.arange(256)[None,:]
HWX = HW[IDX]                      # HWX[u,m] = HW(u ^ m)
U = S[P[:,i] ^ k]                  # 每个明文的 S 盒输出
X = HWX[U]                         # (N, 256)：每个 mask 一列
corr = |oz @ (X - X.mean(0))| / (X.std(0) * N)
```

## 5. 代码逐段解释

| 片段 | 作用 |
|---|---|
| `get(path)` | 每次新建 HTTP 连接发 GET，返回 JSON |
| `recv_idle`（早期版本） | 等响应安静下来再读下一条 |
| `pts = 160 条随机明文` | 提供输入多样性，用于统计相关 |
| `var = win.var(axis=0)` | 找窗口内最敏感的采样点 |
| `U = S[P[:,i] ^ k]` | 枚举密钥：第 i 字节查表输入 |
| `HWX[U]` | 一次性得到 256 种 mask 的汉明重量 |
| `corr` 计算 | 观测幅度与模型的皮尔逊相关 |
| `np.argmax` | 取相关最大的 `(k, mask)` |
| `decrypt_tries` | 枚举流密码拼法，按可打印比例挑正确答案 |

## 6. 为什么这样就成功

| 条件 | 要求 | 满足方式 |
|---|---|---|
| 掩码常量 | mask 在一次采集内不变 | 固定 nonce + 单次采集 |
| 采样点正确 | 泄漏点随明文变化 | 方差排序取前 3 |
| byte 11 可恢 | 掩码跨采集不变 | mode=1 的 sticky 策略 |
| 解密拼法 | 与网关一致 | 枚举 + 可打印打分 |

## 7. 失败尝试与排除

| 尝试 | 结果 | 为什么失败 |
|---|---|---|
| 直接在尖峰顶点做 `HW(S[p^k])` | 相关 0.2 | 顶点不是敏感点 / 被掩码 |
| 8 线程并发采集 | `TimeoutError` | 服务端扛不住并发，必须串行 |
| 靶机过期后继续跑 | `/api/rom` 返回空、JSON 解析报错 | 环境 2 小时到期 |
| 只解 15 字节就解密 | `decrypt hits: []` | 错一个字节全错 |

## 8. 原理

- **CPA**：功耗与数据相关；用猜测密钥算出的中间值做模型，与真实轨迹求相关，正确密钥相关最高。
- **掩码防护**：`v ^ mask` 破坏与真实值的相关性。
- **掩码复用**：mask 固定时，暴力 `(k, mask)` 即可恢复 —— 这正是本题的缺陷。

## 9. 防御

1. 掩码每次新鲜随机，禁止 sticky。
2. 不暴露原始轨迹；加噪声/滤波。
3. 限制采样次数。
4. 校准模式不对外开放。

## 10. 复盘自测

**Q1**：为什么相关系数 0.97 就说明密钥对了？
**A**：正确密钥下模型与真实功耗线性相关；错误密钥的相关接近 0。

**Q2**：为什么 byte 11 在 mode=0 只有 0.34？
**A**：该轮被掩码，mask 由 nonce 决定但未知，模型 `HW(S^m)` 与 `HW(S)` 不相关。

**Q3**：为什么必须先「方差选点」再暴力？
**A**：窗口内多数采样点不含信息；先定位敏感点，才能让暴力有信号。
